# Local Knowledge Base Platform

# 完整部署与开发实施方案

**文档版本：** V2.0
**项目名称：** Local Knowledge Base Platform
**项目定位：** 本地私有化、完全离线、支持外部 API 接入的统一知识服务平台
**目标操作系统：** Ubuntu Server 22.04.6 LTS
**目标 GPU：** NVIDIA Tesla P4 × 2
**数据库：** PostgreSQL + Qdrant + Redis
**后端：** Python FastAPI
**前端：** React + TypeScript + Ant Design
**模型服务：** llama.cpp + 本地 Embedding + 本地 Reranker
**接入协议：** REST API + OpenAI Compatible API + MCP
**部署方式：** Docker Compose
**运行模式：** 完全离线运行

------

# 第一章 项目建设目标

## 1.1 项目定位

本项目建设一套独立的本地知识库服务平台。

平台不仅提供 Web 管理界面，还必须提供完整的对外 API，使其他应用、Agent、业务系统和自动化平台能够直接调用知识库。

系统应当具备以下能力：

1. 文档上传、解析、OCR、切片和向量化。
2. 多知识库创建、管理、授权和隔离。
3. Dense + Sparse 混合检索。
4. RRF 检索结果融合。
5. 本地 Reranker 重排序。
6. 基于知识库内容的 RAG 问答。
7. 文档来源、页码和内容引用。
8. OpenAI API 兼容接口。
9. 标准 REST API。
10. MCP Server。
11. 外部 Agent 工具调用。
12. API Key 管理和权限控制。
13. Python、JavaScript SDK。
14. Webhook 文档处理通知。
15. 完全离线运行。
16. 数据备份、恢复和系统监控。

## 1.2 系统最终形态

系统应当由以下几个部分组成：

| 模块         | 功能                                     |
| ------------ | ---------------------------------------- |
| Web 管理端   | 用户、知识库、文档、模型、API 管理       |
| REST API     | 对外提供知识检索和文档管理               |
| OpenAI API   | 提供兼容 OpenAI SDK 的知识库问答         |
| MCP Server   | 为 Agent 提供标准工具调用                |
| SDK          | 为 Python、JavaScript 等程序提供调用封装 |
| RAG 引擎     | 检索、融合、重排序、上下文生成           |
| 文档处理服务 | 解析、OCR、切片、向量化                  |
| 模型服务     | Embedding、Reranker、LLM                 |
| 数据服务     | PostgreSQL、Qdrant、Redis                |

## 1.3 核心设计原则

- 知识库平台必须独立于具体业务系统。
- 外部系统不得直接访问 Qdrant。
- 外部系统不得直接访问 PostgreSQL。
- 所有外部调用统一经过 API Gateway。
- 所有检索必须执行知识库权限过滤。
- REST、OpenAI、MCP 共用同一套 RAG 服务。
- 文档原始数据必须保留。
- 更换 Embedding 模型时必须支持向量重建。
- 所有模型均从本地目录加载。
- 系统运行期间禁止依赖公网模型服务。
- API 接口必须具有版本管理能力。

# 第二章 硬件与操作系统环境

## 2.1 目标服务器配置

| 硬件     | 要求                      |
| -------- | ------------------------- |
| 操作系统 | Ubuntu Server 22.04.6 LTS |
| GPU      | NVIDIA Tesla P4 × 2       |
| GPU 显存 | 每张 8GB                  |
| CPU      | 建议 16 核或以上          |
| 内存     | 建议 64GB 或以上          |
| 系统盘   | 100GB 或以上              |
| 数据盘   | 建议 1TB SSD 或以上       |
| 网络     | 千兆局域网或以上          |

两张 Tesla P4 的显存是独立的，不能将 16GB 当作单张 GPU 的统一显存使用。

Tesla P4 为 Pascal 架构，Compute Capability 为 6.1，并且采用被动散热设计。

必须保证：

1. 服务器有足够的强制风道。
2. GPU 驱动支持 Pascal。
3. CUDA 与推理框架版本经过验证。
4. Docker GPU Runtime 正常。
5. 模型精度和 Batch Size 经过实际测试。

## 2.2 GPU 分工

推荐初始部署：

| 设备       | 工作负载                                  |
| ---------- | ----------------------------------------- |
| GPU 0      | Embedding                                 |
| GPU 1      | Reranker                                  |
| CPU        | PDF、DOCX、OCR、PostgreSQL、Qdrant、Redis |
| CPU 或 GPU | LLM 推理                                  |

LLM 不应默认与 Embedding、Reranker 争抢显存。

如果需要在 GPU 上运行 LLM，应先测试单卡显存占用、上下文长度、量化格式和推理速度。

## 2.3 系统目录

建议统一部署到：

```
/opt/local-knowledge-base/
```

数据目录：

```
/data/local-knowledge-base/
```

部署前检查：

```
lsb_release -a
uname -r
lscpu
free -h
df -h
lspci | grep -i nvidia
```

# 第六章 基础系统部署

```
sudo apt update

sudo apt install -y \
    curl wget git unzip zip jq \
    ca-certificates gnupg \
    lsb-release build-essential \
    python3 python3-venv python3-pip \
    pciutils htop nvme-cli \
    rsync openssl
```

## 6.2 NVIDIA 驱动

检查 GPU：

```
lspci | grep -i nvidia
```

检查驱动：

```
nvidia-smi
```

检查设备：

```
nvidia-smi -L
```

安装时必须选择支持 Tesla P4 和当前 Ubuntu 内核的驱动分支。

不要直接套用只支持新架构的驱动或 CUDA 容器。

安装驱动后：

```
sudo reboot
```

重新登录后：

```
nvidia-smi
```

必须确认两张 P4 都正常工作。

## 6.3 Docker

```
sudo apt install -y docker.io docker-compose-v2

sudo systemctl enable docker
sudo systemctl start docker

docker --version
docker compose version
```

安装与当前驱动兼容的 NVIDIA Container Toolkit。

配置：

```
sudo nvidia-ctk runtime configure --runtime=docker

sudo systemctl restart docker
```

GPU 容器测试：

```
docker run --rm --gpus all \
  nvidia/cuda:<已验证版本>-base-ubuntu22.04 \
  nvidia-smi
```

这里必须替换成实际经过测试并提前下载的镜像版本。

# 第七章 模型部署

## 7.1 Embedding

首选：

```
BAAI/bge-m3
```

模型目录：

```
models/embedding/bge-m3/
```

要求：

- 中文和英文检索。
- 固定模型版本。
- 本地目录加载。
- 维度记录。
- 支持批量处理。
- 记录模型文件 SHA256。

BGE-M3 的 Dense 向量维度为 1024。

## 7.2 Reranker

首选：

```
BAAI/bge-reranker-v2-m3
```

模型目录：

```
models/reranker/bge-reranker-v2-m3/
```

职责：

对 Dense 和 Sparse 初步召回的候选文本进行相关性排序。

建议单独部署服务：

```
http://reranker:8002
```

## 7.3 LLM

建议使用 llama.cpp。

模型目录：

```
models/llm/
```

服务地址：

```
http://llm:8080/v1
```

至少实现：

```
GET  /v1/models
POST /v1/chat/completions
```

配置：

```
LLM_BASE_URL=http://llm:8080/v1
LLM_API_KEY=change-this-secret
LLM_MODEL=local-model
```

具体模型必须根据 Tesla P4 的 8GB 单卡显存、CPU 内存和实际速度进行选择。

不能假定所有 CUDA 新特性都能在 P4 上使用。

## 7.4 OCR

建议优先 CPU OCR。

支持：

- PDF。
- DOCX 中的图片。
- PNG。
- JPG。
- JPEG。
- TIFF。
- 扫描版 PDF。

解析时必须保存页码、图片位置和原始文件信息。

# 第十一章 混合检索和 RAG

## 11.1 检索流程

```
用户问题
   |
   v
权限验证
   |
   v
Dense Embedding
   |
   +------------------+
   |                  |
   v                  v
Dense Search       Sparse Search
   |                  |
   +------------------+
            |
            v
           RRF
            |
            v
         Reranker
            |
            v
       Top-K Context
            |
            v
       Local LLM
            |
            v
    Answer + Citations
```

## 11.2 初始参数

```
retrieval:
  dense_top_k: 30
  sparse_top_k: 30
  rrf_top_k: 40
  reranker_top_k: 10
  final_top_k: 5
```

这些参数必须通过实际知识库数据集进行评估。

## 11.3 RRF

[
RRF(d)=\sum_{r\in R}\frac{1}{k+rank_r(d)}
]

Dense 和 Sparse 的检索结果分别排序后使用 RRF 融合。

## 11.4 Reranker

输入：

```
pairs = [
    [query, item["content"]]
    for item in candidates
]
```

Reranker 输出分数后按相关性降序排列。

## 11.5 引用机制

每个最终回答必须能够追溯到：

- 文档 ID。
- 文件名。
- 页码。
- 切片 ID。
- 原文内容。
- 检索得分。

当知识库无法提供足够依据时，系统应明确告知用户资料不足，不得伪造引用。

# 第二十二章 安全设计

## 22.1 用户认证

- 密码采用 Argon2id 或 bcrypt。
- JWT 设置有效期。
- 刷新 Token。
- 登录失败限制。
- 管理员权限控制。

## 22.2 API 安全

- API Key 使用安全随机数生成。
- 数据库保存哈希。
- 创建时只展示一次明文。
- 支持禁用和轮换。
- 设置权限范围。
- 设置速率限制。
- 设置每日调用限制。
- 记录调用日志。

## 22.3 知识库隔离

必须在服务端执行权限过滤。

不得只依赖前端传入的知识库 ID。

外部 API、MCP 和 Web 用户必须使用同一套权限校验逻辑。

## 22.4 文档安全

- 文件格式检查。
- 文件大小限制。
- MIME 类型检查。
- 路径穿越防护。
- 恶意文件检测。
- 临时文件隔离。
- 文件哈希校验。

## 22.5 Agent 安全

Agent 不得默认获得任意 Shell 执行权限。

文档内容必须视为不可信输入。

必须防御 Prompt Injection，防止文档中的恶意指令诱导 Agent 越权调用工具。

## 22.6 网络安全

PostgreSQL、Qdrant、Redis 不允许直接暴露公网。

外部接入建议使用：

- 局域网。
- VPN。
- HTTPS。
- 反向代理。
- 防火墙白名单。
